# 파일 구성·처리 경계 검토 — 2026-11-14

이번 검토는 모듈 배치, RX→handler→TX 소유권·검증 경계, 로깅 시험 격리,
문서의 현재/과거 결과 구분을 중심으로 수행했습니다. 모든 경쟁 조건이나 수치 알고리즘의 정형 검증은 아닙니다.

## 현재 유지할 구성

| 경로 | 판단 |
|---|---|
| `fcc_app/src/{application,transport,protocol,tracking,common}` | 처리·통신·wire 규격·추적 계산·공통 도구 구분이 적절하므로 이동 불필요 |
| `pc_sim/` | 프로토콜/파서·시나리오·GUI worker/model 분리가 되어 있음. 별도 simulator 폴더 추가 불필요 |
| `fcc_app/tests/test_*`, `tests/` | C host 시험과 PC Python 시험을 현재대로 구분 |
| `fcc_app/tests/log_stress/` | 이번 시험용 C·설정·실행기를 한곳에 격리. CMake 조건부 포함, 기본/일반 DEBUG에서 제외 |
| `docs/test-results/` | 당시 원시 증거. 실패 기록도 원인·재실행과 함께 보존 |
| `build*`, `.vscode` | 로컬 산출물·개인 설정. gitignore 유지, 공개 저장소에 추가하지 않음 |
| `tools/vscode/README.md` | 팀 공통 안내만 유지 |

지금 당장 삭제해야 할 중복 소스는 발견하지 못했습니다. 날짜별 결과 문서는 현재 설명과 역할이 달라
삭제하지 않습니다. 과거 문서의 당시 미검증 문구도 당시 사실로 유지하고 최신 검증 기록에서 연결합니다.

## 후속 이동·정리 제안

- `docs/test-results/*/*.py`의 과거 단발 스크립트는 증거 재현용으로 보존합니다.
  앞으로 재사용할 실행기는 `tools/hil/` 같은 새 simulator와 겹치는 위치를 만들지 않고
  시험 목적에 맞는 `fcc_app/tests/` 하위에 둡니다. 이번 `log_stress`가 그 예입니다.
- 실보드 시험 실행기가 여러 개로 증가하면 그때 공통 serial capture/flash 모듈을 추출합니다.
  현재 한 실행기를 위해 공통 프레임워크를 만들 필요는 없습니다.
- 날짜별 문서와 raw 파일이 더 늘어나면 `docs/hardware-tests/`로 모으는 이동을 별도로 할 수 있습니다.
  지금 이동하면 기존 링크·블로그 링크를 일괄 수정해야 하므로 유지합니다.
- `CLAUDE.md`의 누적 시험 기록은 장기적으로 검증 이력 링크로 줄일 수 있습니다.
  README는 이번처럼 현재 상태·다음 작업만 유지합니다.

## 남은 처리 경계와 우선순위

1. **TRACK_REPORT 규격**: 현재 STATUS는 통계 조회이고 모든 측정의 처리·추정값을 반환하지 않습니다.
   timestamp, 상태, 거리/방위각, 변화율, 송신 주기와 유실 관측 수단부터 정하면 GUI에서 보드 결과를 비교할 수 있습니다.
2. **반복 WARN 정책**: `frame_handler.c`의 미지원 TYPE/COMMAND/잘못된 payload와
   `uart_rx.c`의 overflow 로그는 반복 시마다 생성됩니다. processor 큐 드롭은 첫 회/100회마다 제한합니다.
   제한할 로그·카운터 보존·요약 주기를 정해야 합니다. 이번 포화 시험 통과가 WARN 폭주 해결을 뜻하지 않습니다.
3. **UART 하드웨어 오류**: RX의 통계는 소프트웨어 링/파서/큐 손실을 집계합니다.
   `uart_callback()`에는 overrun/framing/parity 감지·해제·복구 정책이 없습니다.
   하드웨어 오류 계측 없이 STATUS 0을 물리 바이트 손실 0으로 단정하면 안 됩니다.
4. **큐 정책**: INIT/RESET도 공통 FIFO와 새 요청 드롭 정책을 따릅니다. 제어 유실·오래된 측정 처리 기준은 미정입니다.
5. **TX 완료 의미**: `uart_tx_submit()` 성공은 큐 복사 완료이며 `uart_poll_out()`은 상대 수신을 보장하지 않습니다.
   TRACK_REPORT 송신률을 정한 뒤 큐 포화·집계·복귀 기준을 추가합니다.
6. **자원·지속 부하**: 이번 최고 평균 157Hz와 수 초 시험은 최대 처리율/스택 여유/장시간 안정성 보장이 아닙니다.

기존 기능의 변경 없이 위 항목을 후속 설계 대상으로 남겼습니다.
