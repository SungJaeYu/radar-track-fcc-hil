## 로그 형식 통일 후속 작업

- 애플리케이션·bench 로그 50개를 `항목: key=value` 형식으로 통일했다. 단위는 키에, 오류는 `error`, 사유는 `reason`에 표시한다.
- PERF parser는 새 header/단위 필드와 예전 기록을 모두 지원하며 기존 JSON 키를 보존한다.
- GUI/PC simulator는 진단 로그를 상태 입력으로 사용하지 않는다. Qt GUI 실제 UART/콘솔/CSV 경로와 Python 전체 suite를 확인했다.
- 최종 검증: Python783개+subtest9개, CTest128개, 펌웨어5구성, PERF27/DEBUG11/producer13/전송포화95개 판정 통과. 실제 UART Qt GUI도 확인했다. 일반 이미지 복원 및 STATUS0 확인 완료.
- 최신 검증·원문·복원 상태는 [실보드 회귀](hardware-test-2026-11-22-logging.md)를 우선한다. 위 미검증 표시는 후속 시험 이전의 이력이다.

## 내일 할 순서

1. `git status`와 최신 커밋을 확인한다. 사용자에게 변경 사항과 남은 실보드 검증을 먼저 설명한다.
2. 새 로그와 실행 시간 출력의 짧은 실보드 검증은 완료했다. 결과 문서와 한계를 먼저 확인하고, 다음 개발은 선회 시나리오 설계부터 시작한다.
3. 연산별 표본 수 차이는 실제 predict/correct 호출 여부에 따른다. 5초 로그는 부팅 이후 누적 통계이며, INIT/RESET으로 초기화되지 않는다.
4. 새 계측이 확인되면 선회 시나리오를 설계한다. 여객기/전투기 속도·G·선회 반경 관계와 가정부터 설명한다. 아직 시나리오나 추가 알고리즘 구현은 하지 않았다.
5. 이후 동일 입력에서 알고리즘별 추적 오차와 실행 시간 비교를 진행한다. 인터럽트·선점이 포함된 경과 시간을 WCET나 순수 CPU 비용으로 주장하지 않는다.

## 사용자 작업 원칙

- 검토/설명 요청만으로 코드를 수정하지 않는다. 이번 구현·문서 갱신·커밋·푸시는 명시적으로 요청받았다.
- 주석은 영어로, 코드에서 드러나지 않는 이유/제약에만 작성한다. 복잡한 설명이 필요하면 이름과 구조부터 검토한다.
- 검증·계산·상태 갱신·반환과 lock/처리/unlock 사이를 빈 줄로 구분한다. lock 표시용 중괄호나 추가 들여쓰기는 사용하지 않는다.
- 인자 한두 개인 함수 선언/정의/호출은 한 줄로 유지한다.
- 함수 반환값을 지역 변수로 받은 뒤 조건 검사한다. 암시적 변환에 의존하지 않고 필요한 cast는 범위·부호·손실을 확인한다.
